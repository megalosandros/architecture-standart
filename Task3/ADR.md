### <a name="_u8xz25hbrgql"></a>**Нефункциональные требования**

| **№**  | **Требование**               |
|:------:|:-----------------------------|
| **R**  | **Надёжность (Reliability)** |
| R01    | Доступность системы подачи заявок (сайт + интернет-банк + Deposits Gateway) — 99,9% круглосуточно | 
| R02    | Поддержка отказоустойчивости: автоматическое переключение на резервный ЦОД при недоступности основного. |
| R03    | Система должна корректно обрабатывать ошибки (например, недоступность СМС-шлюза) без потери данных. |
| **P**  | **Производительность (Performance)** |
| P01    | АБС не должна получать прямые запросы от интернет-банка в реальном времени. |
| P02    | Разделение нагрузки между ЦОДами (активный/активный или активный/резервный). |
| P03    | API получения ставок должен отвечать за ≤ 400 мс в 95% случаев при нагрузке 100 RPS. |
| **+R** | **+Ограничения (Restrictions)** |
| +R01   | Все данные, передаваемые между клиентом и сервером (сайт, интернет-банк), защищаются TLS 1.2+. |
| +R02   | Чувствительные данные (ФИО, телефон) шифруются при хранении, их использование логируется. |
| +R03   | Новые сервисы должны быть совместимы с текущими платформами (C#, Java, MS SQL, Oracle, React). |

### <a name="_qmphm5d6rvi3"></a>**Решение**

Вводится новый микросервисный компонент — «Deposits Gateway», который:  
* Принимает заявки от сайта и интернет-банка.
* Хранит заявки в собственной БД (MS SQL).
* Публикует события в шину сообщений (Kafka).
* Обеспечивает безопасность (TLS, валидация, логирование).
* Не взаимодействует напрямую с АБС в реальном времени.  


Решение ввести отдельный микросервис «Deposits Gateway» принято, чтобы изолировать уязвимое ядро банка (АБС) от нагрузки и рисков онлайн-каналов. Прямая интеграция интернет-банка или сайта с АБС невозможна: система перегружена, не имеет API и не поддерживает горизонтальное масштабирование. Deposits Gateway выступает как буфер и адаптер: он принимает заявки, обеспечивает безопасность и отказоустойчивость, а в будущем — станет основой для полной автоматизации. При этом решение использует уже знакомые технологии (Java, MS SQL), минимизирует зависимость от подрядчиков и позволяет реализовать MVP быстро и безопасно.

### <a name="_bjrr7veeh80c"></a>**Альтернативы**

<b>Альтернатива 1. Прямая интеграция интернет-банка с АБС через SQL</b>

<b>Плюсы:</b>
* Быстрая реализация: не нужно разрабатывать новый сервис — достаточно добавить SQL-логику в интернет-банк.
* Минимальные изменения в АБС: ядро не трогается, только открывается доступ к БД.
* Единый источник данных: ставки, продукты, клиенты — всё сразу.

<b>Минусы:</b>

* Высокий риск для стабильности АБС: онлайн-трафик (даже небольшой) может перегрузить и без того нагруженную БД, вызвав сбои в ключевых банковских операциях.
* Нарушение архитектурных границ: логика бизнес-процессов (например, расчёт ставок) «размазывается» между Excel, АБС и интернет-банком — это ведёт к ошибкам и несогласованности.
* Отсутствие масштабируемости: АБС масштабируется только вертикально, а интернет-банк — горизонтально; такая связка создаёт «бутылочное горлышко».
* Сложность поддержки и безопасности: прямой доступ к БД из внешнего приложения — грубое нарушение принципов безопасности (особенно с учётом требований ЦБ к защите данных).
* Жёсткая связанность: любое изменение структуры таблиц в АБС сломает интернет-банк, что парализует развитие обоих систем.


<b>Альтернатива 2. Полная модернизация АБС и переход на микросервисы</b>

Поэтапный переход от устаревшей АБС к современной микросервисной архитектуре с REST API, что позволит напрямую интегрировать интернет-банк и кол-центр.

<b>Плюсы:</b>
* Устранение проблем с производительностью и масштабируемостью.
* Единая платформа для всех каналов.
* Современные технологии облегчают поддержку и развитие.

<b>Минусы:</b>

* Длительный и дорогой проект с высоким риском.
* Требуется значительное обучение персонала.
* Не подходит для быстрого запуска текущего функционала

**Недостатки, ограничения, риски**<br/>

<b>Недостатки и ограничения:</b>
* Дублирование данных: ставки по депозитам, справочник продуктов и заявки временно хранятся вне АБС
* Дополнительная сложность архитектуры: появляется новый распределённый компонент, который требует определенных затрат (CI/CD, мониторинг, управление конфигурацией)
* Задержка в обработке заявок: поскольку интеграция с АБС — асинхронная и ручная на MVP
* Зависимость от Kafka (или другой шины)

<b>Риски:</b>
* Риск фрагментации данных
* Риск недооценки DevOps-нагрузки
* Риск нехватки экспертизы по Java/Spring
